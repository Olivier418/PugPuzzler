# Codebase map

Repo layout: all code is one package, `pugpuzzler/` (subpackages `classes/`, `serialization/`, `plotting/`; modules `constants`, `solving`, `benchmark`, `puzzle_bounds`; `__init__` is a docstring only), installed with `pip install -e .` from `pyproject.toml` (dependencies + `requires-python >= 3.10`; there is no requirements.txt). Editable is required, not a convenience: `constants.ROOT_DIR` is the package's parent, where the data lives. Code outside the package (tests, `tutorial/`) imports `pugpuzzler.<module>`; inside the package, cross-subpackage imports are absolute (`from pugpuzzler.constants import ...`), same-subpackage ones relative. Repo root: `pugpuzzler/`, data (`games/`, `bounds/`; outputs `solutions/`, `benchmarks/`), `tests/` + `run_tests.py`, `tutorial/`, `docs/` (`SOLVER_WALKTHROUGH.md`, `SOLVER_NOTES.md`), `assets/` (images the README uses, e.g. `header_img.svg`; a notebook's images live in `tutorial/images/` instead, so the tutorial folder is self-contained), `README.md`, `LICENSE` (MIT), `CLAUDE.md`. `.vscode/` is git-ignored. Paths below are relative to `pugpuzzler/` unless they name a root folder.

Import layering (no cycles): `constants` <- `classes.kernel` <- `classes` <- `serialization` <- `solving` <- `benchmark` <- `plotting`. `classes` never imports `serialization`; anything needing both lives in `solving.py`/`serialization/`. `classes/kernel.py` is a leaf below the rest of `classes`: it imports only numpy and numba and knows nothing about Setup/Puzzle.

A book's solutions / stats are plain dicts keyed by puzzle name (`dict[str, Solution]`, `dict[str, SolveStats]`); there are no book container classes for them. Only puzzles have one (`PuzzleBook`).

Core model (`classes/`, layered bottom-up):
- `blocks.py` — `Block(positions, letter, terminal_color)` (`positions` a bool mask; coords, ndim, count), `BlockCollection` (UserDict, keys 0..n-1 in the order given -> Block, unique letters). A block's key is also its column in a solution row and its position in the kernel -- there is no translation table. blocks.json entries are `{"letter", "positions", "terminal"}`.
- `boards.py` — `Board(cells, offset_adjacency)` (cells: bool ndarray, shape via `board.cells.shape`; `offset_adjacency[i, j]` = axes i, j offset by half a cell, e.g. a pyramid's layers). Cached `gram2` (twice the axes' Gram matrix, integers) and `unit_vectors` (every direction of unit length, used by `Setup._valid_orientations`). Blocks have no such geometry: their own coordinates are always orthogonal (doubled Gram matrix 2I, written inline in `_valid_orientations`). `RegularBoard(cells=None, width, depth, height=None)`, `PyramidBoard(width, depth)`.
- `setup.py` — `Setup`: board + blocks + **all valid placements** (expensive, computed once, shared by reference across every Puzzle/Book built on it; raises if a block has none). `placement_cells[block_idx]` (a list, one entry per block) = compact cell-index array per valid orientation/position. Compact indexing: grids only cover the board's real cells (`compact_to_flat`/`flat_to_compact`); `to_full_grid(grid)` expands a compact grid to the full board-shaped array (rendering / disk boundaries). `render(grid, header=None, leftover_idcs=None, labels=None, cell_width=2, letters=True, mark=None)` is a thin facade delegating to `rendering.py` (`labels` compact, expanded like the grid; `mark` a compact cell index). Lazy `cached_property` `kernel_tables` (a `kernel.Tables`), built once per Setup and shared by every search on it — a book is 72 puzzles on one Setup, so caching it here rather than per puzzle is worth ~2x on a book solve. The search's *mutable* state (`kernel.Workspace`) deliberately does NOT live here. `warmup()` builds `kernel_tables` and loads the compiled kernel (`kernel.warmup`, once per process); `solving.timed_solve` and `benchmark` call it before their clocks start so numba's ~0.35 s cache load (seconds on a recompile) isn't billed to the first puzzle. `rows_to_grids(rows)` turns solution rows (see `solver.solve_rows`) into full board-shaped int64 grids `(k, *board shape)`, identical to `to_full_grid(puzzle.grid)` for the same solutions; `grids_to_rows(grids)` is its inverse and a validity check (raises unless each block covers exactly the cells of one of its placements -- a placement is matched by its sorted cells as one `ravel_multi_index` key). `row_dtype` (cached): uint16 when every block has < 65,536 placements, the dtype rows are stored in.
- `puzzle.py` — `Puzzle(setup, letter_grid=None, name="", difficulty=None)`: the one mutable board-state class (there is no separate State) -- compact `grid` + `chosen_placement_idx` (block idx -> placement idx or UNPLACED), `name`, `difficulty`, `source`, over a shared `Setup`; optionally pre-filled from a letter grid (`_initialize_grid`, transposes JSON (depth,width) -> internal (width,depth)). `place_unchecked(block_idx, placement_idx)` is the only mutator (writes grid and chosen_placement_idx together; no checked place/remove). `nr_filled_cells` property. `solve_rows(**options)` returns `solver.solve_rows(self, **options)` (yields rows, *returns* whether the search ran to the end); it doesn't print (that's `solving.py`'s job). `solved_copy(row, nr)` (copy + `place_unchecked` every still-unplaced block, named "<name> (solution nr)" when named and nr is given) is the one row -> Puzzle conversion, used by `Solution.__repr__` and `solving` (SHOW_SOLUTIONS). `render(show_leftover=True)` builds header `"Puzzle {name}"` + grid + shape diagrams of any still-unplaced blocks; `__repr__` calls it.
- `puzzlebook.py` — `PuzzleBook(UserDict)` (raises `ValueError` if empty): named collection of Puzzles sharing one Setup (`.setup`), `.source`. `__repr__` expands every Puzzle with `show_leftover=False`.
- `game.py` — `Game`: top-level container of `books` (name->PuzzleBook), `puzzles` (standalone), `setups` (board_key->Setup). One Game per `games/<GameName>/` folder. `board_key(setup)`: a Setup's key (by identity; raises if it isn't the game's) -- how `save_puzzlebook`/`save_bounds` find the board of books they are handed.
- `source.py` — `Source` (frozen dataclass): game/book/puzzle name triple recording where a Puzzle/Book was loaded from. `relative_dir()` -> `<game>/books/<book>` (book), `<game>/puzzles/<puzzle>` (standalone), `<game>/books/<book>/<puzzle>` (one puzzle out of a book). Set by the `serialization.games_io` loaders and `save_puzzlebook`, `None` for hand-built objects.
- `solutions.py` — pure data, no solving or I/O: `SolveStats` NamedTuple (puzzle_name, options, seed, duration, complete, elapsed -- in that order, which is also the stats.json key order; `options` = free-form solver kwargs besides the seed (`branch`, `order`), kept to tell solver variants apart in benchmarks; only options that leave the solution set alone belong there; `complete: bool` = the run found every solution (True) or was cut short by `time_limit`/`max_solutions` (False), always recorded; `duration`/`elapsed` are rounded to `constants.TIME_DECIMALS` (6, i.e. 1 us) where they are taken -- `timed_solve` and `benchmark`'s trial, the only two places a SolveStats is built -- so memory and disk agree exactly and stats files stay compact). `Solution(puzzle, rows)`: every solution as a row of placement indices -- the solver's own form, ~20x smaller than a grid, so even an empty board's 4.3M solutions fit in ~100 MB; `grids` is a property building full board-shaped grids on each access, `len()` is the solution count, `__repr__` renders them via `puzzle.solved_copy(row, i)` (headers "Puzzle <name> (solution i)"); grids exist only at the edges: solutions.json and printing; **always holds its live `puzzle`** — the one solved, or the one `load_run_books` found in `games/` — so `puzzle_name`/`setup` are properties and difficulty/filled cells are read off `sol.puzzle`.
- `solver.py` — the thin Python driver around `kernel.py`, one generator function: `solve_rows(puzzle, seed=None, time_limit=inf, max_solutions=inf, order=None, branch="both")` yields every solution as a row -- every block's placement index, pre-placed ones included, in block order -- stopping early once either limit is hit, and *returns* True if the search ran to the end (kernel DONE), False if a limit cut it short (becomes `SolveStats.complete`). It holds the kernel loop and turns each kernel return's global-id paths into rows on top of `base` (the pre-placed columns), as a fresh array so kernel re-entry can't touch yielded rows. It owns only what the kernel cannot see: `_start()` turns the puzzle's grid + already-placed blocks into the kernel's `(occ, used)`; `_resolve_rules()` resolves `branch`/`order` to integer codes and raises `ValueError` on anything else. **Laziness**: the kernel is never told `max_solutions`; it gets a solution-buffer cap and a node budget, returns FULL/BUDGET/DONE, and is re-entered with its stack intact. An EMA of nodes/s sizes ~2 ms chunks, which is how `time_limit` stays exact to ~2 ms and how the generator stays abandonable mid-tree. Each generator allocates its own `kernel.Workspace`, so searches never share state. **`branch`** picks which kind of item a node branches on (see `kernel.choose_item`): `"both"` (default, the scarcer of the two), `"cell"`, `"block"` — `"block"` is a baseline only, hopeless on an open board; `"cell"` is the tests' reference. Neither is used outside tests. **`order`** (`True`/`False`/`None`) ranks a node's candidates by their cells' live-placement counts (`kernel.RANK_COUNTS`); because `kernel.rank` keys off a *placement* and never learns which kind of item was branched on, it applies uniformly to all three `branch` modes. `None` = on iff a limit is set. Seeded with `order=False` sorts by the drawn priority alone, since the branch argmin leaves nothing for a seed to perturb. (`"pockets"`/`"fanout"` rankings were removed 2026-09-28; the benchmark numbers are in `SOLVER_NOTES.md` §2, and `order="counts"` is no longer accepted.) `docs/SOLVER_WALKTHROUGH.md` is a read-alongside guide to both files; `docs/SOLVER_NOTES.md` has the measurements and what was removed (symmetry, partitioning, two rankings) and why.
- `kernel.py` — the search itself, compiled by numba; no `classes` imports. A cell is a bit: occupancy is `occ`, `NW = ceil(n_cells/64)` uint64 words, and `pmask[gid]` is the same for a placement, so the conflict test is one AND per word. `nw` is read from `occ.shape[0]` at runtime and looped over, so there is **no cell-count ceiling and no separate path for big boards** — 55 cells and IQquub's 64 both give NW 1; a 200-cell board gives NW 4 and works. `Tables` (per Setup, via `Setup.kernel_tables` = `build_tables(placement_cells, n_cells)`, block positions = the list's indices, ~70 KB): `pmask`, `pblock`, `pcells`, `psize`, CSR `cell_start`/`cell_pl`, `block_start`, `full`, `n_cells`, `n_blocks`, `fan` = `max(cell degree, block run)` so both kinds of candidate list fit one buffer. Rank rules: `RANK_NONE`, `RANK_PRIORITY` (seeded `order=False`), `RANK_COUNTS` (`order=True`). `Workspace` = one search's mutable state, allocated per `solve_rows` generator. `kernel()` is an **iterative explicit-stack DFS** — numba recursion segfaults, and a stack is what makes the run resumable; every `return` happens with the loop invariant intact, so re-entry is just "run the loop again". `occ == full` is the only termination test: `Setup._validate_area` guarantees the blocks' total area equals the board's, so covering every cell implies placing every block — and the converse, which is what makes `branch="block"` terminate. A placement is its own undo (`^=`). `choose_item` returns `(kind, index)` — kind 0 a cell, 1 a block position — and is what a node costs, not the conflict test; `_count_cell`/`_count_block` cap their scans at the best-so-far count, which is what makes MRV affordable. **Debugging: `NUMBA_DISABLE_JIT=1` runs this exact source as plain Python** (~1300x slower, pdb works) — that is why there is one implementation and no NumPy reference. It constrains the source: index the `BIT` table instead of shifting (numpy 2 promotes `uint64 << int` to float64) and write every literal `np.uint64(...)`. All helpers are module-level — a closure cell would be hashed into numba's `cache=True` key and `benchmark.py`'s trial subprocesses would recompile. `warmup(t)` (idempotent, module flag) compiles/loads once: `benchmark.py` calls it in the parent so trial subprocesses don't race, and in each worker before its "ready" handshake.
- `rendering.py` — terminal display: `grid_lines`, `block_shape_lines`, `legend_lines`, `render(board, blocks, grid, header=None, leftover_idcs=None, labels=None, cell_width=2, letters=True, mark=None)`. Plain `Board`/`BlockCollection`/grid args, no `Setup` dependency. The options (all off by default; `solver_trace` uses all but `mark`): `labels` (board-shaped plain strings, drawn right-aligned in EMPTY cells), `cell_width` (chars per cell; `_widen` stretches the 2-char edge tokens so the outline stays continuous), `letters=False` (placed blocks as plain color), `mark` (a board coordinate: `◀` after its row, `▲` under its column).
- `_utils.py` — `_assert_unique` (block letters, a book's puzzle names).
- `__init__.py` — the public re-export surface; import from here, not submodules, in new code.

Serialization (`serialization/`, three modules; imports `classes`). `__init__` exports what outside code uses: `load_game`, `load_puzzle`, `save_puzzlebook`, `next_run_dir`, `save_run`, `load_run_books`, `load_complete_run`, `write_stats`, `load_stats`, `Bounds`, `save_bounds`, `load_bounds`. Everything outside imports from the package, never from submodules.
- `jsonio.py`: leaf letter-grid helpers. A grid is one string per row (`"BBB        "`), a pyramid a list of such layers; `" "` = empty/off-board. `parse_letter_grid` (rows -> str array as written), `block_grids_to_rows(grids, blocks)`/`rows_to_block_grids(entries, blocks, shape)` (a batch of full grids of block indices `(k, *shape)` <-> letter-row entries via the blocks' letters, vectorised through one byte string and a lookup table -- seconds for millions of grids; the reader raises on a wrong-sized entry or an unknown letter), `dump_json(obj, path)` (indent 2, a list of strings one row per line aligned under the first, a list of scalars on one line).
- `games_io.py`: the `games/` folder. `load_blocks`/`load_boards`, `load_setups(game_dir)` ({board_key: Setup}; lru-cached per resolved game dir per process (`_setups`, the dict copied per call), so everything loaded from a game -- `load_game`, `load_run_books`, `load_complete_run` -- shares the same Setup objects, which `Game.board_key`'s identity match, and so `save_bounds`/`save_puzzlebook`, rely on; games/ never changes, so it can't go stale), book files (`{"board", "puzzles": [{"name", "difficulty", "grid"}]}`; `"board"` is required -- there is no bare-list format and no default board) via `load_puzzles(file, setups)` / `write_puzzles(puzzles, board_key, file)`, `load_book(game_dir, book_name, setups)`, `load_standalone_puzzles(game_dir, setups)` (`puzzles/*.json` = `{"board", "difficulty"?, "grid"?}`), `load_game(dir)` (auto-discovers `books/*.json` + `puzzles/*.json`, builds a full `Game`); every loaded book/puzzle gets its `Source`. `load_puzzle(json_file, game)`: a puzzle file in the standalone format kept *outside* `games/` (e.g. `tutorial/demo_puzzle.json`), on the game's Setup for its board, named after the file stem, no `Source` (solvable and printable; its runs can't be saved). `save_puzzlebook(book, game, games_root=GAMES_DIR)` is the inverse for a book made in memory (e.g. `compute_puzzle_bounds`): writes `games/<game>/books/<name>.json` (never overwrites), sets the Sources, adds it to `game.books` — a run can only be saved for puzzles that live in `games/`. Names are never read from a JSON `"name"` field except for puzzles inside a book file: `Game.name` = folder name, `PuzzleBook.name`/standalone `Puzzle.name` = file stem. A boards.json entry needs `"type"` (`RegularBoard`/`PyramidBoard`) and its dimensions, no defaults; a RegularBoard's `"cells"` (instead of width/depth) is row strings (`"X"` = cell), transposed in `_parse_board`.
- `results_io.py`: everything solving produces. **One layout per file, whether it holds one puzzle or a book**: `solutions.json` = `[{"puzzle_name", "grids": [letter grid, ...]}, ...]` (`write_solutions`/`load_solutions(file, puzzles)`: grids built `_CHUNK` (65,536) rows at a time on the way out; every grid read back through `Setup.grids_to_rows`, so every loaded solution is checked to be one), `stats.json` = `[{"puzzle_name", "options", "seed", "duration", "complete", "elapsed"}, ...]` (`write_stats(stats)` = `SolveStats._asdict()` per entry, `load_stats(file) -> dict[str, SolveStats]` = `SolveStats(**entry)`; `complete` is required). Paths: `next_run_dir(source, root, prefix="result")` -> `<root>/<Source.relative_dir()>/<prefix>_<max idx + 1>` (raises for a source-less puzzle/book, pointing at `save_puzzlebook`; `benchmark` prefix for benchmarks; the newest run always has the highest idx), `_game_book(folder)` (game/book of a run folder, anchored on its nearest `books`/`puzzles` component). Runs: `save_run(solutions, stats, folder)` (dicts keyed by puzzle name; either may be None, not both) / `load_run_books(folder, games_root=GAMES_DIR) -> (PuzzleBook, dict[str, Solution] | None, dict[str, SolveStats] | None)` — three parallel mappings keyed by the same puzzle names; a missing file loads as None (raises if both are missing). A run stores no puzzles and no game/book names: its path names game and book, the files name the puzzles, and the Puzzles are always loaded from that game under `games_root` (`load_book`/`load_standalone_puzzles` on the game's shared Setups, see `games_io.load_setups`; ~0.05 s a game), whichever halves exist; `games/` is fixed (existing puzzles never change; `save_puzzlebook` only adds books), so a run can't go stale. The PuzzleBook holds only the puzzles the run covers, named after the book (or the one standalone puzzle). There is deliberately no `game=` shortcut: a run only ever refers to puzzles in `games/`; tests use `games_root` on a copied game. `load_complete_run(folder, puzzle) -> (Solution, SolveStats)`: the way to pick up a run of one puzzle (e.g. an empty board's, for `compute_puzzle_bounds`) -- the user passes the run folder, and it raises unless that folder sits under `<root>/<puzzle.source.relative_dir()>/`, holds both files, its stats name `puzzle` alone and say `complete`, and every solution keeps the puzzle's pre-filled pieces in place (cheap checks first, solutions read last); the Solution is attached to the `puzzle` passed in. There is no "find the latest run" helper: which run to use is the caller's choice. Bounds: `save_bounds(game, lower, upper, root=BOUNDS_DIR) -> folder` (the board is the books' Setup, via `game.board_key`; overwrites) / `load_bounds(game, board_key, root=BOUNDS_DIR) -> Bounds` (`Bounds` = `(lower, upper)`, each a `(PuzzleBook, dict[str, SolveStats])`, the books named `LOWER_BOUND_BOOK`/`UPPER_BOUND_BOOK`; raises `FileNotFoundError` unless all four files exist) -- `<root>/<game>/<board_key>/{lower,upper}_puzzles.json` (book-file format) + `{lower,upper}_stats.json` (every puzzle's, the empty board's included -- self-contained, so deleting runs in `solutions/` never breaks them). Nothing computes bounds as a side effect of loading, or loads them as a side effect of computing.
- On-disk layout: `games/<Game>/{blocks.json, boards.json, books/*.json, puzzles/*.json}`; solutions mirror it under `solutions/<Game>/<books|puzzles>/<name>/[<puzzle_name>/]result_<idx>/{solutions.json, stats.json}`; benchmarks under `benchmarks/<Game>/<books|puzzles>/<name>/[<puzzle_name>/]benchmark_<idx>/<config-label>/stats<seed>.json` (one stats file per trial, one entry each; no solutions); each board's solution bounds under `bounds/<Game>/<board_key>/{lower_puzzles.json, lower_stats.json, upper_puzzles.json, upper_stats.json}` (the empty board's solutions they come from are an ordinary run of `empty_<board_key>` in `solutions/`). `solutions/` and `benchmarks/` are git-ignored; `bounds/` is tracked (IQpuzzler main, ~9 MB, so `tutorial/2_findings.ipynb` loads rather than computes them). Everything there was converted to the one-layout format on 2026-09-28 (old book runs and the IQquub puzzle runs were re-solved to get a `complete` flag; benchmark trials got `complete` = found every solution of the empty board, and `{"order": "counts"}` became `{"order": true}`, folder `order`); the benchmark folders `order=pockets`/`order=fanout` hold trials of the removed rankings.

Running (`solving.py`, `benchmark.py`):
- `solving.py` (saves via `serialization.save_run`): `timed_solve(puzzle, seed, verbose, time_limit, max_solutions, keep_rows=True, progress=False, **options) -> (rows | None, SolveStats)` is the one timing path (solve_puzzle and puzzle_bounds use it, so their times compare): `setup.warmup()` off the clock, then `puzzle.solve_rows` driven by hand (to catch its return value, the `complete` flag) with one elapsed stamp per solution (rounded to `TIME_DECIMALS`) and the `verbose` printing on it (at `SHOW_SOLUTIONS`, `puzzle.solved_copy(row, i)` is printed); rows gather in a doubling numpy buffer (`_RowBuffer`, `setup.row_dtype`), not a list, since an empty board can have millions. An empty board's solutions are just an ordinary run in `solutions/` of the game's standalone `empty_<board_key>` puzzle (IQpuzzlerPRO main: 4,331,140 solutions, ~416 MB of JSON, ~40 s to read or write): `solve_puzzle(game.puzzles["empty_main"], save_solutions=True, save_stats=True)` once, then `load_complete_run("solutions/<Game>/puzzles/empty_main/result_<idx>", puzzle)`. `solve_puzzle(puzzle, seed, verbose, save_solutions, save_stats, solutions_root, time_limit, max_solutions, progress=False, **options) -> (Solution, SolveStats)` and `solve_puzzlebook(book, ..., progress=False) -> (dict[str, Solution], dict[str, SolveStats])` (one combined save; `progress` there is a bar over puzzles). Solves and times (`timed_solve`), wraps the rows in a Solution and, only with `save_solutions` and/or `save_stats` (opt-in, independent: the grids are the bulk of a save and the stats are useful without them), saves that half to `next_run_dir(source, solutions_root)` (mirroring the `Source`; there is no `path=` argument, tests pass `solutions_root=tmp`). `time_limit`/`max_solutions` are deliberately not part of `options` (never recorded or treated as a benchmark config): they change which solutions come back, not how they are found. `verbose` is a `Verbosity` IntEnum (cumulative): `SILENT` 0; `SUMMARY` 1 "Found 21 solutions to puzzle x in 1.23s"; `EACH_SOLUTION` 2 also "Found 3rd solution to puzzle x in 0.42s" per solution; `SHOW_SOLUTIONS` 3 prints each solved puzzle instead of that line (its header already names puzzle + solution number). The summary line ends every level >= 1 (at level 3 it omits "to puzzle x" when a puzzle was rendered above it).
- `benchmark.py`: `run_benchmark(...) -> ({ConfigKey: [SolveStats]}, folder)`/`load_benchmark(folder)` (same dict: globs `*/stats*.json`, groups by `config_key(stats.options)` in config-folder order, each group sorted by the entries' own `seed`; no `game`, since no Puzzles are needed), `config_key`/`config_label` (a config = dict of solver keyword options; `DEFAULT_CONFIGS` = `({"order": True}, {"order": False})`). Trials run in a subprocess with a wall-clock cap `T`: the parent owns the authoritative deadline and kills the worker, which also gets `time_limit=T`. The worker solves on `solve_rows`, starts its clock when it sends "ready" (when the parent starts T), stamps each solution itself and sends the stamps in batches at most every `_BATCH_SECONDS` (10 ms; one pipe message per solution cost ~20% throughput), never the solutions, then `("done", (duration, complete))`; the parent waits up to T + `_GRACE_SECONDS` for that, keeps stamps <= T, caps the duration at T and builds the trial's `SolveStats` (complete only if the search ended within T; stamps and duration rounded to `TIME_DECIMALS` after the T comparisons), saved with `write_stats({name: stats}, ...)`. Only stats are saved. Takes a `Puzzle` that lives in `games/` (has a `source`).

Plotting (`plotting/`): every plot takes stats as any `Mapping[str, SolveStats]` (plain dicts). `plot_puzzle_stats.py`: `plot_puzzle_stats(puzzles, stats, x=None, y=None, z=None, title=None, ax=None)` is the one general one-dot-per-puzzle scatter (one dot per entry of `stats`; `puzzles` is any name -> Puzzle mapping covering them, e.g. `load_run_books`'s PuzzleBook or the book that was solved -- `solved_puzzles` does the lookup and raises `ValueError` for a missing name; no plot takes solutions, since none reads a grid), colored by difficulty (`difficulty_color`: the game's tiers from `DIFFICULTY_COLORS`, the bounds' tags from `BOUND_COLORS`; `legend_entries` = the difficulties present, in that order); `z` makes it 3D (log axes become log10 with 10^k tick labels, since 3D can't log-scale). Axes are named `Metric`s from `METRICS` (`nr_filled_cells` (default x), `nr_solutions`, `time_to_first_solution`, `time_to_last_solution`, `solve_time`; `nr_solutions` is `len(stats.elapsed)`), or a custom `Metric(label, value(puzzle, stats), log)`. Puzzles with an undefined value (nan) or a non-positive one on a log axis are dropped. Difficulty/nr_filled_cells are read off the puzzle; puzzles on the same point (values + color) are consolidated into one dot labeled with all their names; an existing `ax` is an overlay: it remembers its metrics (`ax._puzzle_stats_metrics`), so `x`/`y`/`z` are inherited (naming a different one raises), and its legend is extended, not rebuilt. `format_axes(ax, metrics)` and `style_2d(ax)` are the shared look. `plot_solve_timeline.py`: `plot_solve_timeline(puzzles, stats) -> Figure` is deliberately standalone: one subplot row per difficulty (tier order, shared log y), one column per puzzle, one mark per *solution*; every row has as many column slots as the largest tier, so columns are equal width and left-aligned; reuses `difficulty_color`/`style_2d` (minus bottom spine, x ticks and vertical grid). `plot_bounds.py`: `plot_bounds(lower_puzzles, lower_stats, upper_puzzles, upper_stats, title=None, ax=None)` draws `compute_puzzle_bounds`' result on filled cells vs. number of solutions (log): fixed axis limits (autoscaling off, so overlays can't rescale), `OUT_OF_BOUNDS_COLOR` shading below the lower and above the upper bound, a dashed black line along each with a small unnamed black dot (a line marker, smaller than `plot_puzzle_stats`' dots) on each of the bounds' own puzzles; the axes are labelled, styled and given `_puzzle_stats_metrics` via `format_axes` exactly as `plot_puzzle_stats` would; returns the ax, onto which `plot_puzzle_stats(book_puzzles, book_stats, ax=ax)` overlays a real book of the same board. `plot_benchmark.py`: `plot_benchmark(trials, show_trendline=True)` (`{ConfigKey: [SolveStats]}`, as `run_benchmark`/`load_benchmark` return) draws each trial's cumulative-solutions step curve (anchored at (0,0)) plus the per-config average on a 500-point grid, colored from `constants.CONFIG_PALETTE`; Trendline rate = `_poisson_rate`, the homogeneous-Poisson MLE (total solutions / total observed time, pooled over trials).

`puzzle_bounds.py`: `compute_puzzle_bounds(empty_solution, empty_stats, verbose=True) -> Bounds` = `((lower_puzzles, lower_stats), (upper_puzzles, upper_stats))` (stats as dicts keyed by puzzle name), pure: no files read or written, always computes; the input is a complete solve of an empty puzzle (raises if the puzzle isn't empty, the stats aren't its, or `complete` is False), whose Solution carries the puzzle and hence the Setup/board. Keep the result with `save_bounds`, read it back with `load_bounds` -- the bounds on the number of solutions: for every attainable filled-cell count from 0 (the empty board, included) to one block short of full, a puzzle with the exact fewest solutions (lower bound, tagged `HARDEST_DIFFICULTY`) and one with the exact most (upper bound, `EASIEST_DIFFICULTY`), one example per count even where the bound is 1, named 1, 2, 3, ... by increasing filled count. Books `LOWER_BOUND_BOOK`/`UPPER_BOUND_BOOK` (`"lower_bound"`/`"upper_bound"`, the same on every board); no solutions. Loading them back takes IQpuzzler main 0.4 s, IQpuzzlerPRO main ~4 s (puzzle 1's stats hold 4.3M stamps). Puzzle 1's SolveStats are `empty_stats`. A realization's solutions are the rows placing its blocks its way, so `bound_counts(table, n_placements, sizes)` (pure, public for tests) groups the rows per block subset -- `_Grouping.dfs` grows a subset by one higher column at a time, refining the parent's group ids with `np.unique` (no solver calls). A singleton group settles every superset's lower bound at 1 (`settle`, realized from its row); once that holds below a node only the upper bound is left, so only rows in groups larger than every reachable filled count's best upper bound are passed on (exact: child groups never outgrow their parent's) -- ~8x faster than grouping every subset. `_bound_puzzles` builds a book from a bound (via `place_unchecked`); `_time_bound_book` re-solves its non-empty puzzles with `timed_solve` for their SolveStats, each count checked against the grouping's.

`tutorial/solver_trace.py` (demo-only, used by `tutorial/1_solver.ipynb`, imported from the notebook's working directory `tutorial/`): replays the search one node at a time with the kernel's own primitives (`solver._start`, `kernel.choose_item`, `_count_cell`/`_count_block` uncapped, `collect_cell`/`collect_block`), so it can't drift from the solver. `Step(kind, index, cell_counts, block_counts, candidates)` (`kind` "cell"/"block", candidates as `(block_idx, placement_idx)`); `branch_step(puzzle)` (one node), `walk(puzzle) -> (nodes, solved)` (the search up to its first solution exactly as the solver runs it -- branches tried in candidate order, the kernel's unranked order, dead ends included -- as `(depth, puzzle, step)` per visited node, plus the solved puzzle or None; checked to reach `next(solve_rows())` on every IQpuzzler book puzzle), `describe(nodes, solved)` (`walk`'s result as a tree indented by depth: a node per line with its branch count, a dead end / forced move on an extra-indented line, `forced --> *solution!*` under the solution's parent, a closing `...` under the deepest node with branches left), `render_cell_counts(puzzle, step)` (every empty cell's count on the board, placed blocks as plain color, cells widened to fit the counts), `render_block_counts(puzzle, step)` (every unplaced block drawn in full, its count underneath), `render_branches(puzzle, step)` (a one-line header naming the chosen item, then every branch's board side by side, headed `branch i` in the order they are tried). Only what the notebook uses is kept.

`tutorial/` holds the tutorial, two notebooks committed with outputs (they run from `tutorial/` and import the installed package, so each one's first code cell is just imports -- `solver_trace` from the working directory -- and loading the games it needs; neither depends on the other's state): `1_solver.ipynb` (the algorithm, game-agnostic -- IQpuzzler's pieces and main board are only its running example, loaded as `game`: the game, placements, packing as exact cover, the search as Knuth's Algorithm X (bitmasks instead of dancing links), the solver walk on the demo puzzle via `solver_trace.py` next to it, under the hood) and `2_findings.ipynb` (the applications: Part I introduces IQpuzzler -- its booklet, its main bounds, the fewest cells for a unique puzzle; Part II introduces IQpuzzlerPRO as the revamped sequel promising a unique solution per puzzle -- its boards, the check of that promise; the summary), the box picture `images/IQpuzzler_main.png` `2_findings` shows, and `demo_puzzle.json`, a made-up main-board puzzle (3 blocks left, unique solution) loaded with `load_puzzle`, chosen so `walk` shows the whole search in four nodes with one-digit counts: block C (2 branches, a strict minimum) -> branch 1 -> cell (7, 2) (2 branches, strict) -> branch 1 is a dead end -> branch 2 -> forced last block -> solved (no booklet puzzle comes close; it was found by stripping 3 blocks off random empty-board solutions). The notebooks compute everything themselves, except that `2_findings` loads the tracked IQpuzzler main bounds with `load_bounds` (computing them is a commented-out cell).
